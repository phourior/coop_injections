# 全图视野与经验倍率：SC2 版本升级维护指南

> 当前验证版本：`SC2_x64.exe Base97579`  
> 对应实现：`Dll1/hooks/game_hook.cpp`、`Dll1/render/menu.cpp`

## 一、维护原则

SC2 更新后，不能只把旧 RVA 加上新模块基址。RVA、RIP-relative 位移、函数序言、寄存器分配和内部结构偏移都可能变化。维护这两个功能时应分别证明：

1. 找到的仍是同一个语义位置，而不只是字节相似。
2. Hook 函数的调用约定和参数位置没有变化。
3. 经验 payload 的字段布局没有变化。
4. 写入补丁后，被替换指令的边界和后续控制流仍然成立。
5. 所有验证失败时功能保持关闭，不回退到未经验证的固定地址。

建议保留每个已支持版本的 `SC2_x64.exe` 哈希、完整版本号、目标 RVA、目标函数反汇编和测试结果。RVA 用于分析对照，不作为运行时唯一定位手段。

## 二、当前实现基线

### 2.1 全图视野

Base97579 的补丁点位于：

```text
SC2_x64.exe + 0x1CD7A79
```

原始 10 字节：

```text
48 8D 0D 90 0E 37 02 8B 34 81
```

对应指令：

```asm
lea rcx, [rip+visibilityTable]
mov esi, [rcx+rax*4]
```

补丁字节：

```text
BE FF FF FF FF 90 90 90 90 90
```

即：

```asm
mov esi, 0FFFFFFFFh
nop
nop
nop
nop
nop
```

当前 pattern：

```text
48 8D 0D ?? ?? ?? ?? 8B 34 81 48 89 6C 24 ??
41 80 FD 10 74 ?? 44 0F A3 EE
```

前 10 字节是实际替换范围，后续字节只用于确认上下文。四字节 RIP 位移、栈偏移和短跳转距离已经通配。

全图视野 checkbox 是自动模式总开关，不代表补丁始终写入。`OnGameLobbyUpdate`
每次更新时读取 `GameLobby+0x08` 的地图路径和 `GameLobby+0x18` 的显示标识，
对两段 UTF-8 字符串做子串匹配。进入以下 15 张合作地图时自动应用补丁，离开
或切换到不支持的地图时自动恢复原字节：

```text
虚空撕裂  克哈裂痕  虚空降临  往日神庙  湮灭快车
天界封锁  升格之链  熔火危机  机会渺茫  营救矿工
亡者之夜  黑暗杀星  净网行动  聚铁成兵  死亡摇篮
```

代码分别保存“用户请求开启”和“补丁已应用”两个状态。这样可以在大厅先勾选，
进入支持地图后再自动写入；离图时恢复补丁但保留总开关，下一张支持地图会再次
自动应用。菜单中的状态文字用于区分“等待支持地图”和“已应用”。

### 2.2 经验倍率

Base97579 中已确认 5 个同源 Hook 入口：

| 序号 | SC2 RVA |
|---|---:|
| 0 | `0x1F9FC50` |
| 1 | `0x26C80C0` |
| 2 | `0x2700380` |
| 3 | `0x27134D0` |
| 4 | `0x27307D0` |

这些 RVA 仅用于核对扫描结果。运行时代码扫描公共函数序言，最多容纳 8 个入口。

经验 Hook 当前假定：

```text
第三个参数            payload 指针
payload + 0x18        ExperienceEntry* entries
payload + 0x20        uint64_t count
ExperienceEntry 大小  0x80
entry + 0x08          uint8_t active
entry + 0x09          uint64_t value（非对齐）
count 合理范围         1..16
```

修改发生在调用 original trampoline 之前。经验值采用整数乘法，并在溢出时饱和为 `UINT64_MAX`。

## 三、升级后的第一轮检查

更新 SC2 后先不要开启功能。注入 DLL，收集日志并检查：

```text
[*] Experience: found N candidate hook target(s)
[+] Experience hook[i] created at ...
[*] FullMapVision patch addr: ...
```

结果解释：

| 现象 | 含义 | 处理 |
|---|---|---|
| Fog pattern 找不到 | 指令被重编译或上下文变化 | 重新定位，不使用旧 RVA |
| 经验目标为 0 | 序言或 CALL 后数据流变化 | 重新定位同源处理函数 |
| 经验目标仍为 5 | 只是候选数量相同 | 仍须验证函数签名和 payload |
| 经验目标不是 5 | 可能新增/删除路径，也可能误命中 | 逐个反汇编并检查调用者 |
| `MH_CreateHook` 失败 | 入口指令不适合 trampoline 或地址错误 | 检查函数边界与 MinHook 日志 |

当前代码在 pattern 失配时保持功能不可用，这是预期的安全行为。不要为了“先能用”而加入固定 RVA fallback。

## 四、更新全图视野

### 4.1 在新版中重新定位

推荐顺序：

1. 在旧版 IDA 中打开 `SC2_x64.exe+0x1CD7A79`，记录所在函数、调用者和交叉引用。
2. 使用 BinDiff、Diaphora 或相邻稳定函数，在新版中找到对应函数。
3. 确认目标逻辑仍从一个表中按索引取得 32 位位掩码，并将结果保存在后续位测试使用的寄存器中。
4. 沿后续基本块确认该值参与可见性或迷雾位判断，而不是无关的数组读取。
5. 确认准备覆盖的指令总长度至少为 5 字节，且必须按完整指令边界覆盖。

不要仅搜索 `8B 34 81`。该指令过短，在大型模块中很可能有多个无关命中。

### 4.2 重新制作 pattern

从目标指令向前后保留足够上下文，然后按以下规则处理：

- RIP-relative `disp32` 必须通配。
- `CALL/JMP rel32` 的目标位移必须通配。
- 栈偏移、短跳转距离只有在确认会随编译变化时才通配。
- 表达核心数据流的 opcode、索引比例和目标寄存器尽量保留。
- pattern 必须在整个新版模块中唯一命中。

若新编译器改变了目标寄存器，例如从 `ESI` 变成 `EDI`，不能只修改补丁首字节。必须跟踪后续代码实际读取哪个寄存器，再生成对应的 `mov reg32, 0FFFFFFFFh`。

### 4.3 验证补丁长度

当前补丁恰好替换 7 字节 `LEA` 和 3 字节 `MOV`。新版若出现以下变化，需要重新计算长度：

- `LEA` 被拆成多条指令。
- 表读取改成不同寻址模式。
- 编译器在两条核心指令之间插入其他有副作用的指令。
- 后续存在跳转进入被覆盖区域中部。

新的补丁长度、备份数组长度、`VirtualProtect` 长度和 `FlushInstructionCache` 长度必须一致。

### 4.4 运行时验证

在合作模式的测试环境中执行：

1. 开启前保存目标地址至少 32 字节。
2. 开启后确认仅预期范围变化。
3. 验证己方、敌方、未探索区域和小地图表现。
4. 关闭后逐字节确认原始内容完全恢复。
5. 重复开启/关闭至少三次。
6. 在地图加载中、已入图和离图后分别测试。
7. 按 `END` 卸载，确认代码字节已恢复且进程稳定。

## 五、更新经验倍率

经验功能比 Fog 更容易出现静默数据破坏，因为 pattern 命中不代表 payload 布局仍然正确。

### 5.1 重新确认 Hook 集合

从 Base97579 的 5 个入口做函数相似度匹配。新版每个候选都要确认：

1. 是函数入口，而不是函数中段。
2. x64 调用约定仍可描述为四个寄存器参数。
3. 第三个参数 `R8` 仍传递同类经验 payload。
4. 五个或更多入口最终消费相同的数据结构。
5. Hook 前修改 payload，不会使同一事件被多个入口重复放大。

如果调用链变化导致同一个 payload 连续经过两个已 Hook 入口，经验会被乘两次。应通过断点记录 payload 地址、线程 ID 和调用栈，确认一次事件只修改一次；必要时把 Hook 收敛到更靠近公共消费点的单一函数。

### 5.2 重新确认 payload

在新版中对经验为 `1`、小值和较大值的事件分别抓取 payload，验证：

- `payload+0x18` 指向可读数组。
- `payload+0x20` 是稳定、合理的条目数。
- 相邻条目间距确实为 `0x80`。
- `entry+0x08` 与条目是否有效相关。
- `entry+0x09` 的 8 字节值与实际增加经验一致。
- 字段是整数而不是指针、浮点数、变长编码或校验值。

可以先把 detour 改成只记录、不写入，比较 Hook 前后的 payload 快照。只有字段语义被多次样本验证后，才恢复写入。

### 5.3 更新扫描特征

当前扫描结构为：

```text
[固定函数序言]
E8 ?? ?? ?? ??
[固定 CALL 后数据流]
				  ; 函数起点 +0x2B
41 B0 0E          ; mov r8b, 0Eh，经验事件类型
```

其中 `CALL rel32` 只检查 `E8`，目标位移不参与匹配。Base97579 中仅使用序言和 CALL 后数据流会命中 164 个模板函数；加入 `+0x2B` 的事件类型约束后才精确命中 5 个经验入口。`0x4480` 是 Base97579 的栈帧大小，不是业务语义；编译器改变局部变量布局后，这组特征可能失配。

更新时优先保留：

- 保存非易失寄存器的整体结构。
- payload 参数从 `R8` 保存或传递的路径。
- 与经验条目处理相关的稳定调用或字段访问。

优先通配：

- CALL/JMP 的相对位移。
- RIP-relative 全局位移。
- 栈帧大小和局部变量偏移。

如果多个函数仅序言相同，应增加函数中段的语义验证，不能继续依赖“取前 8 个”。更稳妥的长期方案是先定位公共经验消费函数，再从其调用者交叉引用生成 Hook 列表。

### 5.4 运行时验证矩阵

至少测试以下组合：

| 场景 | 倍率 | 预期 |
|---|---:|---|
| 普通经验事件 | 1 | 与未开启一致 |
| 普通经验事件 | 2 | 增量为原值两倍 |
| 多条目事件 | 3 | 每个 active 条目各乘一次 |
| 无效条目 | 30 | inactive 条目不修改 |
| 大数值 | 30 | 不发生整数回绕 |
| 关闭功能 | 任意 | payload 原样传给 original |
| 重复开关 | 1/30 | 不重装 Hook、不崩溃 |
| DLL 卸载 | 任意 | detour 先停用，再由 MinHook 清理 |

测试时同时核对游戏最终显示值和 detour 中观察到的原始增量，避免把 UI 累计动画误认为真实经验值。

## 六、建议增加的长期防护

当前实现适合已验证版本。若需要长期跨版本维护，建议按优先级增加：

1. **唯一命中扫描 API**：返回命中数量，Fog 只有恰好一个候选才允许写入。
2. **版本指纹表**：记录 PE 时间戳、映像大小和 `.text` 哈希，区分已验证与未知版本。
3. **只读诊断模式**：未知版本只输出候选地址和 payload，不执行写入。
4. **结构探针**：经验开启前采样多个 payload，检查指针、数量和字段范围。
5. **Hook 去重**：记录短时间内已处理的 payload 地址，检测同一事件是否经过多个入口。
6. **补丁所有权检查**：恢复 Fog 前确认目标字节仍等于本 DLL 写入的补丁，避免覆盖其他模块后续修改。
7. **自动化离线扫描**：构建时对保存的多个 SC2 版本统计 pattern 命中数并输出 RVA。

其中第 1、3、6 项能直接降低未知版本误写代码段的风险，应优先实现。

## 七、故障处理

### Fog 开启失败

检查日志是否为 `pattern not found`。若是，按第四章重新定位。若能找到地址但写入失败，检查页面保护、目标字节和进程中是否有其他补丁模块。

### 经验 checkbox 自动恢复为关闭

`SetupExperienceHooks()` 没有成功创建任何 Hook。先查看候选数量和 `MH_CreateHook` 错误，不要直接改成旧 RVA。

### 经验异常放大

优先怀疑同一 payload 被多个 Hook 连续处理，其次检查 `entry+0x09` 是否仍是原始增量。记录调用栈和 payload 地址后再缩减 Hook 集合。

### 游戏在开启功能时崩溃

立即保持功能关闭，并检查：

- pattern 是否命中函数中段或无关函数。
- Fog 覆盖范围是否切断指令。
- 经验函数签名和第三参数是否变化。
- payload 指针和条目数组是否属于可读写内存。
- 卸载清理是否发生在 `MH_Uninitialize()` 之前。

在上述语义验证完成前，不应通过放宽 pattern 或移除边界检查来绕过失败。
